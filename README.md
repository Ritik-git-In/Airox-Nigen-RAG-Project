# PDF RAG Assistant

A Streamlit-based Retrieval-Augmented Generation (RAG) bot that answers questions from your uploaded PDF documents. It extracts text from PDFs, splits content into citeable chunks, stores them in a local Chroma vector database, and uses the Kimi/Moonshot AI model to generate answers with source citations.

## 1. Project Title and Description

**PDF RAG Assistant**

This bot helps users ask natural-language questions across a collection of PDFs. It returns answers supported by source citations, including file names and page numbers, by combining local document retrieval with an LLM for answer generation.

## 2. Tech Stack

- Python 3.11+ (recommended)
- Streamlit >= 1.40
- pypdf >= 5.0
- chromadb >= 0.5
- onnxruntime >= 1.16
- openai >= 1.50
- python-dotenv >= 1.0
- pymupdf, pytesseract (OCR fallback for scanned pages — see [OCR setup](#10-ocr-for-scanned-pdfs))

## 3. Architecture Overview

The RAG pipeline in this project is:

1. **Ingestion**
   - User uploads PDFs through the Streamlit UI.
   - `rag/pdf_loader.py` extracts text per page while preserving page metadata.
2. **Chunking**
   - `rag/chunking.py` divides each page into overlapping chunks to preserve context and avoid slicing sentences in half.
3. **Embedding**
   - `rag/embeddings.py` converts chunks into embeddings using the local ONNX MiniLM model (`all-MiniLM-L6-v2`).
4. **Vector storage**
   - `rag/vectorstore.py` stores embeddings in a persisted ChromaDB collection keyed by user.
5. **Retrieval**
   - At query time, the user question is embedded and the most-similar chunks are retrieved from ChromaDB.
6. **Generation**
   - Retrieved chunks are sent to Kimi/Moonshot via `rag/llm.py` to generate an answer that cites the source text.

## 4. Chunking Strategy

This app uses a greedy character-window chunking strategy with overlap:

- `CHUNK_SIZE = 1000` characters
- `CHUNK_OVERLAP = 150` characters

Why this strategy?

- It keeps chunks small enough to retrieve precise local context.
- Overlap prevents important concepts or sentence fragments from being split across chunks.
- It is fast and consistent for document text of varying structure, especially PDFs where page breaks and formatting can vary.

## 5. Embedding Model and Vector Database

- **Embedding model**: `all-MiniLM-L6-v2` via ChromaDB's ONNX embedding function.
  - Chosen because it is light, fast, and runs locally without PyTorch.
  - Produces 384-dimensional vectors that work well for semantic search over document text.
- **Vector database**: ChromaDB.
  - Chroma stores embeddings on disk in `data/chroma/`, making retrieval persistent across restarts.
  - It is easy to integrate with the local embedding model and supports the similarity search used by the RAG pipeline.

## 6. Setup Instructions

Follow these steps to clone and run the project locally.

```powershell
# 1. Clone the repository
git clone https://github.com/Ritik-git-In/RAG-document-Q-A-bot.git
cd "RAG-document-Q-A-bot"

# 2. Create a Python virtual environment
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure environment variables
Copy-Item .env.example .env
# Edit .env and add your KIMI_API_KEY

# 5. Run the app
streamlit run app.py
```

Once Streamlit opens, log in with your email, upload PDFs, wait for indexing, and then ask questions.

## 7. Environment Variables

The project reads configuration from `.env` at the repository root.

Required variables:

- `KIMI_API_KEY` — your Kimi/Moonshot API key.
- `KIMI_BASE_URL` — API base URL (default: `https://api.moonshot.ai/v1`).
- `KIMI_MODEL` — model to use for generation (default: `moonshot-v1-32k`).
- `EMBEDDING_MODEL` — local embedding model name (default: `all-MiniLM-L6-v2`).
- `CHUNK_SIZE` — character chunk size (default: `1000`).
- `CHUNK_OVERLAP` — overlap between chunks (default: `150`).
- `TOP_K` — number of document chunks retrieved per question (default: `10`).

**Important:** never commit real API keys to Git.

## 9. Known Limitations

- **Not a perfect legal or financial advisor**: answers are generated by an LLM and may require verification.
- **Long documents**: only the top `TOP_K` chunks (plus each hit's same-page neighbor chunk) are sent to the model, so some relevant context can be missed if the answer spans many pages.
- **Private local embeddings only**: this implementation is built for local use and does not include multi-user deployment hardening beyond per-user collections.
- **Model dependency**: answer quality depends on the Kimi/Moonshot model and its prompt handling.

## 10. OCR for Scanned PDFs

A page with little or no text in the PDF's own text layer (a scanned book,
report, or photographed document) is automatically OCR'd instead of being
skipped. This needs Tesseract OCR installed as a **system binary** — the
`pymupdf` and `pytesseract` Python packages in `requirements.txt` are not
enough on their own:

1. Install Tesseract:
   - **Windows**: download the installer from the
     [UB-Mannheim Tesseract build](https://github.com/UB-Mannheim/tesseract/wiki)
     and run it (default install path works fine).
   - **macOS**: `brew install tesseract`
   - **Linux (Debian/Ubuntu)**: `sudo apt install tesseract-ocr`
2. Make sure the `tesseract` command is on your `PATH` (the Windows
   installer offers to do this — check the box).
3. Verify it: `python -c "import pytesseract; print(pytesseract.get_tesseract_version())"`

If Tesseract isn't installed, OCR is skipped automatically and the app
behaves as it did before this feature — scanned pages just don't
contribute text to the index, with no error.

## 11. Bulk-Indexing a Large Drive (Terabyte Scale)

For indexing a large collection (hundreds of thousands of PDFs, multiple
terabytes) — more than is practical to run through the Streamlit UI's
"Scan Drive" option — use the standalone command-line tool instead. It's
decoupled from the Streamlit app's session, so a scan that runs for hours
or days isn't at risk from a browser tab closing or the app restarting:

```powershell
python scripts\bulk_index.py you@example.com E:\ --workers 8
```

- `--workers` controls how many files are extracted/OCR'd in parallel
  (default: CPU core count − 1). Embedding and database writes happen in
  the main process to avoid multiple processes writing to the same SQLite
  file at once.
- Safe to interrupt (`Ctrl+C`, power loss, crash) and re-run with the exact
  same command — every file's result is committed to disk the moment it's
  indexed, so a re-run picks up exactly where it left off instead of
  starting over.
- List available drives first with `python scripts\bulk_index.py --list-drives`.
- The Streamlit app can be used normally (to ask questions) while a bulk
  index is running in a separate terminal — they share the same on-disk
  vector store and catalog.

### Resource planning

Rough guide (see `rag/config.py` for `CHUNK_SIZE`, and note the vector
index needs to fit in RAM):

| | Per 1 million chunks |
|---|---|
| RAM (vector index) | ~2.5 GB |
| CPU-only embedding time | ~1–2 hours |
| GPU embedding time (`onnxruntime-gpu`) | ~10–15 minutes |

A "chunk" is roughly 2–3 per page. How many pages your collection turns
into depends heavily on document density — the most reliable way to plan
capacity is to bulk-index a representative sample first and extrapolate
from its actual chunks-per-GB.
